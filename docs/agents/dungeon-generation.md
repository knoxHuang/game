# 新增神祇副本

用户说“新增某某外神副本”“补齐某副本美术”或“生成眷属”时，执行本流程。交付目标是一套可运行且通过验收的副本包。

## 1. 确认来源与造型

1. 阅读根目录 AGENTS.md、游戏主设计和 `src/content/schema.ts`。查看已确认的大厅背景，以及目标副本已有资产。
2. 联网核对神祇及眷属的原著描述。优先使用原著全文；采用后世作者或桌游设定时标明版本。记录作品名、具体 URL 和支持造型/关系的证据摘要。
3. 在 `lore` 中区分原创与改编。原著未确定的结构、颜色、弱点、职业和从属关系，在 `interpretation` 与眷属 `relationship` 中标为游戏改编。不能把“都有触手”当成共同造型。
4. 先确定身体结构、轮廓、材质、识别部位、比例、环境和攻击动作，再生成图片。神祇本体、显现、化身或眷属首领的身份必须与实际关卡一致。

完成条件：来源足以支持已声称的原著特征；补充设计明确标注，`lore.reviewed` 如实记录审阅结果。

## 2. 建立副本包

每个副本对应 `src/content/dungeons/<id>.json`。字段、数值范围和已支持行为以 `src/content/schema.ts` 为唯一依据。可参考现有 JSON 的结构；三个历史包是原型，不是完整美术范例。

- 新增稳定、唯一的英文小写 id，文件名与 id 一致。现有 id 关联存档，不得改名或删除。
- 配置名称、地点、危险等级、推荐属性、开放条件和不重叠的海图位置。
- 配置三种眷属：`beast` 为近战扑击，`bug` 为弹道远程，`cultist` 为地面法术。这些键是行为槽，不规定生物外观。各槽可有独立名称、生命、射程、速度、攻击、掉落与美术。
- Boss 可组合 2–4 段 `ground` 落点和 `fan` 扇形弹幕。分别配置阶段、预警/恢复时间、伤害和攻击参数。
- 使用 `schemaVersion: 3`。在 `combat.waves` 配置全副本五波的绝对开始秒数、各类怪物总量、`batches` 批次数和 `batchInterval` 秒数；各类数量是整波总量，由引擎均分到各批次；前四波普通怪，第五波只有一个 Boss。残敌不阻止下一波，Boss 不依赖设施等级或抵达固定地点。
- 使用 `arena` 配置战区名称、宽高、入口、整体背景、全局障碍、危险区和设施。首区为20×24单位，入口(10,14)。镜头跟随两轴，移动不触发波次。生成点位于当前可见交战区四周，使用 `combat.warning` 预警与 `combat.safeDistance` 安全距离。
- 普通波最后一批必须早于下一波开始；第五波仅一个 Boss，`batches: 1`、`batchInterval: 0`。整局最多160只普通怪加一只Boss，首区当前调优预算112只普通怪。总量、出怪频率与攻击密度需一起验收。
- 保留撤离信标，各区、生成点与设施之间保持可走通道。障碍与场景图中的实体对齐。
- v3 的场地宽18～28、长20～32单位可配；三类普通行为、材料类型和案件目录固定。新增机制、超范围地形尺寸、材料或案件需要先扩展引擎与规格，再写配置。不得通过未知字段、脚本字符串或已有行为冒充实现。

完成条件：数据能通过 `npm run content:check`；新增普通内容不需要修改 Boss 名单、UI 分支、存档白名单或战斗条件判断。

## 3. 生成全套美术

使用可用的 imagegen 技能及其工具。所有图片参照已确认的大厅，保持精细像素纹理、光照层次和旧式调查题材。共用 UI 继续使用木质、黄铜和铜金文字。

**副本环境独立设计。** 神祇决定建筑、空间、地貌、天象、材质和主色。统一的是绘制方式、像素密度、可读性和界面材质；不是把所有场景固定成同一片蓝绿海港。不能只给旧场景换色就交付新副本。

### 战斗辨识与提示词

生成前，把背景、主角、三种眷属、Boss 和攻击特效作为一组设计。检查现有黄色雨衣主角和目标场景，分别确定主色、明度、饱和度与轮廓。将选择写入已有的资产来源记录，并带入对应提示词。画风一致不等于各层使用相近的主色和明暗。

- **背景**：可走区域使用较低的局部对比和纹理密度。大面积地面与黄色雨衣、敌人主体形成色相或冷暖差异，并保留明度差异。暖灯、湿地反光和装饰亮点集中在外围，亮度与面积服从战斗主体；保留地形和障碍的可读性。
- **主角**：保留黄色雨衣及帽子、背包轮廓。地面和怪物主体避开同面积、同明度的黄褐色。局部黄铜或灯光可以保留，但不能形成假主角轮廓。
- **敌人**：按各自主题选择与主角可区分的主体色。每种眷属和 Boss 的身体、四肢与武器在脚下地面上都应有清楚边缘。主题需要相近色时，用明度、材质和克制的边缘光分离；不能只靠小眼睛、血条或锁定圈辨认敌人。
- **特效与掉落**：敌方攻击、生成预警、玩家弹道和战利品同时用形状与明暗区分。背景装饰避开近似的高亮图案，减少动态效果时仍能辨认危险。

以下片段供后续生成使用。先填入本副本的实际配色与明暗关系，再并入资产提示词；参考图分别注明是造型、画风还是配色依据。

>

> Effects: Separate enemy danger, player shots, and loot through shape and value as well as hue. Preserve static danger cues with reduced motion.

接入后，在 320×480、360×640、414×896 的真实战斗尺寸检查同屏效果。让主角、三种眷属和 Boss 分别经过地面最亮、最暗和纹理最密处，并检查敌群重叠与攻击预警。对运行截图追加灰度检查，确认主体轮廓不只依赖色相。普通模式和减少动态效果均须通过；孤立透明图或放大的母图不能替代此检查。

若主体与地面融为一体，或需要寻找血条才能发现敌人，辨识验收失败。调整对应资产的配色、明暗或局部细节后复查；不能仅将整张背景压黑，也不能仅增加粗光圈掩盖问题。通过前不将 `art.reviewed` 或 `status: ready` 标记为完成。

### 资产规格与接入

运行资产放在 `public/assets/dungeons/<id>/`；母图与生成记录放在 `art-source/dungeons/<id>/`，母图不进入运行时加载目录。生成工具的默认保存位置不能直接作为游戏引用。

| 运行资产 | 规格与用途 |
| --- | --- |
| `portrait.webp` | 128×128，≤64 KiB。头部或代表性形态特写；背景简化，缩小后仍可区分 |
| `card.webp` | 384×576，≤384 KiB。独立构图的完整形体、主题环境与尺度参照 |
| Boss 图集 | 透明 PNG/WebP，方形单帧建议256或512。每张≤2 MiB |
| 三种眷属图集 | 透明 PNG/WebP，方形单帧建议64或128。每张≤2 MiB |
| 战区背景 | 宽高各为场地单位数×32像素，≤768 KiB。20×24战区使用640×768，完整俯视构图 |
| 地面、边墙、障碍 | 单图最大256×256，≤128 KiB。用于场景组合与碰撞实体 |
| 弹道与落点特效 | 透明图，最大256×256，≤128 KiB。弹道源图朝上，渲染器负责转向 |

同一副本引用的运行资产总量≤12 MiB。不要用完整场景插画直接充当头像或透明战斗角色。头像、绘图卡、图集分别构图，但共享同一造型设定。

图集必须明确 `frameSize`、`fps`、`anchor` 和七种动作帧：`idle`、`chase`、`windup`、`attack`、`recover`、`hurt`、`defeat`。帧号按行从0开始。待机和移动循环；其余动作停在末帧；死亡表现窗口为0.45秒。动作不能靠每帧随机改变造型实现。

背景只包含环境，不烘焙玩家、动态敌人、界面文字、示例数值或攻击预警。场地各方向保持连通，保留绕行与退路；遮挡实体与 `obstacles` 对位。战斗视角采用俯视角；绘图卡可采用表现尺度的插画视角。

为每项资产记录用途、提示词、参考图、生成/编辑工具、原始文件、运行文件和导出处理。在 `art-source/dungeons/<id>/README.md` 汇总来源、造型依据与视觉检查。使用外部素材时记录来源与允许的用途。

完成条件：头像、卡图、Boss、眷属、背景、地形和特效全部接入对应配置，并且实际渲染；视觉审阅后才能将 `art.reviewed` 设为 true。

## 4. 验收与交付

1. 运行 `npm run content:check`。命令检查结构、未知字段、引用文件、尺寸、透明、帧号、预算、路线连通和海图标记间距，并生成运行目录。
2. 运行 `npm test` 和 `npm run build`。修改攻击机制时补充正常流程、边界及存档恢复测试。
3. 在真实游戏中选择副本。检查名称、画像、卡图、危险评估、战区背景、碰撞、三种眷属、Boss 两阶段、掉落、撤离及失败重生。必须覆盖不清怪到下一波、残敌在战区中追击、预警中重载不重复刷怪、五波 Boss 就地出现和胜利后攻击停止。检查320×480、360×640和414×896，保留运行截图。
4. 以大厅基准复核像素质感；以原著复核造型；以同一角色设定复核头像、卡图、战斗图的一致性。执行[战斗辨识与提示词](#战斗辨识与提示词)的同屏与灰度检查。缩到实际头像尺寸检查，不只审查母图。静态校验不能证明这些视觉和语义判断。
5. 完整时把 `status` 设为 `ready`，运行 `npm run content:ready -- <id>`。未完成时保持 `prototype`，列出缺失项；不得降低校验标准或把旧占位图改名为新美术。
6. 交付副本 id、配置位置、运行截图、素材与来源记录、检查结果，以及仍需补充的内容。

已有三个包保留 `prototype`，允许继续试玩。后续完整新增请求必须通过目标包的 `content:ready`；全量 `content:ready` 在所有历史包补齐前会失败，这是预期结果。

## 示例请求

> 新增犹格·索托斯副本。按项目副本生成规则核对原著，设计其显现与对应信徒，生成数据、头像、绘图卡、Boss与三种眷属图集、主题战区背景和特效，接入游戏并完成校验与手机截图验收。
